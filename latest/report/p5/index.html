    P5. Версионирование опубликованных результатов¶

    Реализация¶

    Версионирование выполняет утилита mike (пакет mike==2.2.0 добавлен в requirements.txt). Каждая версия собирается из своего git-коммита и складывается в отдельный каталог ветки gh-pages, из которой затем формируется артефакт GitHub Pages.

    Элемент Реализация
    Инструмент mike 2.2.0
    Ветка публикации gh-pages
    Раскладка <версия>/, latest/ (алиас), versions.json, index.html (редирект в latest/)
    Тип алиаса copy — символьные ссылки не гарантированно разыменовываются при публикации артефактом и через rsync
    Переключатель версий штатный для темы Material (extra.version.provider: mike)
    Алиас стабильной версии latest переводится на новую версию при публикации (--update-aliases)
    Триггер публикации push тега v* → workflow Publish version

    Настройка в mkdocs.yml:

    extra:
  version:
    provider: mike
    default: latest
    alias: true

    При provider: mike тема Material подключает встроенный переключатель: он читает versions.json из корня сайта, определяет текущую версию по URL, показывает её в шапке и при переключении версии открывает ту же страницу в выбранной версии (для этого в каждой версии публикуется sitemap.xml). Собственный селектор mike для Material не используется: в mike 2.2.0 тема material не зарегистрирована в точке входа mike.themes, поэтому второй (устаревший) селектор в разметку не попадает и конфликта двух переключателей нет.

    Привязка публикации к git-тегу¶

    Workflow .github/workflows/version.yml запускается на push тега, начинающегося с v:

    Шаг Действие
    Checkout fetch-depth: 0 — нужны ветка gh-pages и теги
    Run experiment pipeline scripts/run_experiment.py — результаты пересчитываются из данных тегированного коммита
    Build Sphinx subsite, Build site sphinx-build, затем mkdocs build --strict как контроль качества
    Deploy version to gh-pages mike deploy --push --update-aliases --alias-type copy "$TAG" latest
    Export published site git archive gh-pages \| tar -x -C _published
    Upload Pages artifact, deploy публикация содержимого gh-pages в GitHub Pages (upload-pages-artifact + deploy-pages)

    Публикация версии выполняется командой:

    git tag v1.1
git push --tags

    origin в репозитории имеет два push-URL (GitHub и GitVerse), поэтому тег попадает в оба репозитория; workflow публикации версий находится в GitHub-репозитории. Помимо тега workflow имеет workflow_dispatch с параметрами version и update_latest — для повторной публикации уже существующей версии без создания нового тега.

    Две версии с различающимися результатами¶

    Версия собирается из состояния тегированного коммита, поэтому различие результатов обеспечивается различием данных data/experiment.csv между коммитами:

    1. git tag v1.0 && git push --tags — публикуется текущее состояние данных.
    2. Изменить значения в data/experiment.csv, например 0.0,2.5092 → 0.0,3.1000.
    3. git commit -am "Changed experiment data" && git tag v1.1 && git push --tags.

    Вторая публикация переводит алиас latest на v1.1, при этом каталог v1.0/ остаётся неизменным: mike перезаписывает только каталог публикуемой версии.

    Проверка¶

    Переключатель версий и алиас¶

    Проверка Ожидаемый результат
    https://bobrall.github.io/pyweb/ редирект в latest/
    https://bobrall.github.io/pyweb/versions.json список версий, у v1.1 есть алиас latest
    Шапка страницы переключатель с версиями dev, v1.1 latest, v1.0
    Переключение версии на странице «Эксперименты» открывается та же страница в выбранной версии
    https://bobrall.github.io/pyweb/latest/experiments/ те же значения, что в v1.1
    https://bobrall.github.io/pyweb/v1.0/experiments/ значения версии v1.0 (не меняются при публикации v1.1)

    Локальная проверка публикации¶

    Проверка выполнена в отдельном клоне репозитория: сборка конвейера, затем

    .venv/bin/mike deploy --update-aliases --allow-empty --alias-type copy v1.0 latest
.venv/bin/mike set-default --allow-empty latest

    После публикации второй версии в ветке gh-pages находятся каталоги v1.0/, v1.1/, latest/, файл versions.json и index.html с редиректом в latest/. Результаты эксперимента в версиях различаются:

    Параметр v1.0 v1.1
    Данные 0.0,2.5092 0.0,3.1000
    Начальная амплитуда \(A\) 2.4306 2.5808
    Постоянная затухания \(\tau\), с 4.0939 3.9803
    \(R^2\) (в лог-шкале) 0.9957 0.9919

    Значения v1.1 соответствуют изменению 0.0,2.5092 → 0.0,3.1000; при другом изменении данных значения будут иными, но различие версий сохраняется.

    Порядок в versions.json и редирект корня¶

    [
  {"version": "dev", "title": "dev", "aliases": []},
  {"version": "v1.1", "title": "v1.1", "aliases": ["latest"]},
  {"version": "v1.0", "title": "v1.0", "aliases": []}
]

    Текущая сборка основной ветки публикуется как версия dev, поэтому в списке она стоит выше нумерованных версий, а корень сайта ведёт в latest/ — стабильную ссылку на последнюю опубликованную версию.

    Связь с P3 и P4¶

    Задание Что даёт версионирование
    P3 Версия собирается из тегированного коммита: страница «Эксперименты» в v1.0 и v1.1 содержит разные версии набора данных и разные параметры подгонки, метка версии сборки указывает коммит и хеш данных
    P4 Helios продолжает обслуживать сборку main и preview-каталоги веток; версии публикуются в GitHub Pages, откат версии выполняется публикацией предыдущего тега
    T5 Постоянные ссылки: адрес latest/... не меняется при выходе новых версий, а адреса v1.0/... и v1.1/... неизменны для конкретного результата

    Ограничения¶

    • Ссылки без версии (https://bobrall.github.io/pyweb/experiments/) после первой публикации версии перестают работать: постоянные адреса — latest/… и vX.Y/…. На Helios корень по-прежнему отдаёт сборку main без версий, поэтому там ссылки без версии сохраняются: mike формирует относительные ссылки от корня сайта и раскладывать версии в подкаталоги чужого сайта не умеет.
    • Повторная публикация старого тега по умолчанию переведёт на него алиас latest (так работает --update-aliases); для исправления уже выпущенной версии используйте ручной запуск workflow с update_latest: false.
    • Артефакт для Helios формируется из сборки до публикации версии, поэтому канонические URL и sitemap.xml в нём указывают на корень GitHub Pages, а не на каталог версии.
    • GitHub Pages отдаёт артефакт, собранный из gh-pages, поэтому источник Pages остаётся «GitHub Actions»; при выборе источника «Deploy from a branch» достаточно ветки gh-pages.
    • GitVerse Pages публикует сборку main без версий: пайплайн GitVerse не работает с веткой gh-pages, она исключена из триггеров выражением branches: [ '**', '!gh-pages' ].
    • Подкаталог Sphinx копируется в каждую версию хуком hooks/copy_sphinx.py, поэтому полный артефакт версии содержит и страницы MkDocs, и стресс-страницу Sphinx; вес одной версии — около 14 МБ, из них основная часть — ресурсы Sphinx и Material.
