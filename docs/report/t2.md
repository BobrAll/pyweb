# Т2. Анализ конвейера «эксперимент → артефакт → страница»

## Введение

Проанализированы способы попадания результатов вычислений на страницы статического сайта. Сравнение по пяти подходам: ручные PNG, исполнение ноутбуков (nbconvert, MyST-NB, Quarto), papermill, генерация артефактов скриптом (Makefile/nox). Отдельно — ограничения CI для тяжёлых вычислений.

## Обоснование весов критериев

- **Вес 5**: воспроизводимость, связь с версией данных, связь с версией кода.
- **Вес 4**: автоматизация, кэширование, скорость сборки, отладка.
- **Вес 3**: зависимости, сложность настройки, гибкость, укладывается ли в лимиты CI.

## Детальный анализ

### 1. Ручные PNG

Скрипт строит график локально, PNG коммитится, вставляется в Markdown.

**Плюсы**: минимум зависимостей, быстрая сборка, просто отлаживать.
**Минусы**: не воспроизводимо, нет связи с кодом и данными, легко забыть обновить.
**Когда**: одноразовая публикация без требований к воспроизводимости. Для науки — **неприемлемо**.

### 2. nbconvert / MyST-NB / Quarto

Ноутбук исполняется при сборке, вывод встраивается в страницу.

**Плюсы**: полная воспроизводимость, автоматизация, кэширование ячеек.
**Минусы**: тяжёлые зависимости (Jupyter, Quarto), медленная сборка, съедает лимиты CI, плохо мержится в git.
**Когда**: вычисления лёгкие, данные маленькие, укладывается в лимиты CI.

### 3. papermill

Параметризует ноутбуки: шаблон + разные параметры.

**Плюсы**: удобно для серий экспериментов, параметры сохраняются в метаданных, гибко.
**Минусы**: Jupyter + papermill, кэширование вручную, растёт время сборки.
**Когда**: серии однотипных экспериментов (гиперпараметры, кросс-валидация).

### 4. Скрипт + Makefile/nox

Вычисления — обычным Python-скриптом. Читает CSV, строит графики и генерирует `.md`. Вызывается через `make figures` перед `mkdocs build`.

**Плюсы**: полная воспроизводимость, лёгкие зависимости (pandas + matplotlib), быстрая сборка, кэш через хеш, простая отладка, явная связь с версией данных и кода, укладывается в лимиты CI.
**Минусы**: нет интерактивности Jupyter, надо писать генерацию `.md` самому.
**Когда**: большинство случаев публикации результатов. **Самый практичный подход.**

## Ограничения CI для тяжёлых вычислений

| Ограничение | GitHub Actions | GitVerse | SourceCraft |
|---|---|---|---|
| Лимит минут | 2000/мес (приватные), безлимит (публичные) | 1000/мес | 1000/мес |
| Таймаут job | 6 часов | 1 час | настраивается |
| GPU | ❌ | ❌ | ❌ |
| Кэш | до 10 ГБ | 1–5 ГБ | 1–5 ГБ |
| Размер артефакта | до 500 МБ | до 100–500 МБ | до 100–500 МБ |

**Следствие**: обучение модели в CI невозможно. Только лёгкие вычисления на CPU.

## Граница между стратегиями

**Вычисления в CI** — когда:
- Данные маленькие (КБ–десятки МБ).
- Вычисления секунды–минуты.
- Нет GPU.
- Результаты < 500 МБ.

**Вычисления отдельно, CI собирает из артефактов** — когда:
- Данные большие (> 500 МБ).
- Вычисления длительные (> 10 минут).
- Нужен GPU.
- Жёсткие лимиты минут.

**Гибрид** (самый практичный): тяжёлые вычисления — локально или на своём сервере, результаты коммитятся. В CI — только построение графиков из готовых данных.

## Связь результата с версией кода и данных

### 1. Хеши датасетов

```python
import hashlib
from pathlib import Path

def dataset_hash(path):
    return hashlib.sha256(Path(path).read_bytes()).hexdigest()[:8]
```

На странице: `Версия данных: a3f5c1e8`. При изменении данных хеш меняется — видно, что результат устарел.

### 2. Версии датасетов

Хранить большие датасеты отдельно: DVC, Git LFS или Zenodo (с DOI). На странице — ссылка на конкретную версию.

### 3. Метаданные запуска

`run_metadata.json`, коммитится вместе с результатами:

```json
{
  "commit": "7f6f704",
  "dataset_hash": "a3f5c1e8",
  "dataset_version": "v1.0",
  "params": {"n_estimators": 100, "random_state": 42},
  "started_at": "2026-09-17T14:32:00Z",
  "python": "3.13.5"
}
```

### 4. Отображение на странице

```
| Параметр | Значение |
|---|---|
| Коммит | 7f6f704 |
| Версия данных | v1.0 (a3f5c1e8) |
| Дата сборки | 2026-09-17 14:32 UTC |
| Параметры | n_estimators=100, random_state=42 |
```

Это требование задания Р3.

## Вывод

**Оптимальный подход** — генерация Markdown и CSV отдельным скриптом через **Makefile** или **nox**.

Обоснование:
1. Полная воспроизводимость: код и данные в репозитории.
2. Лёгкие зависимости: Python + pandas + matplotlib.
3. Быстрая сборка, не съедает лимиты CI.
4. Кэш через хеш: не изменилось — пропускаем пересчёт.
5. Явная связь с версией данных и кода.
6. Простая отладка и тесты.
7. Маленькие артефакты, короткие job.

**Условия изменения**:

1. **Уже есть ноутбуки** → **MyST-NB** или **nbconvert**, но дороже по времени и зависимостям.
2. **Серия экспериментов с параметрами** → **papermill** (для скриптов достаточно `argparse`).
3. **Однотипные эксперименты по шаблону** → **Quarto** с `params` и `freeze`.
4. **Тяжёлые вычисления (GPU, часы)** → стратегия «вычисления отдельно, CI собирает из артефактов». Результаты коммитятся, CI только собирает сайт.
