# P4. Развёртывание на Helios

## Схема доставки

Сайт собирается в GitHub Actions командой `mkdocs build --strict`, затем артефакт `site/` публикуется на Helios по SSH через `rsync`.

| Ветка | Путь публикации | URL |
|---|---|---|
| `main` | `${HELIOS_PATH}` | `${HELIOS_URL}` |
| любая другая ветка | `${HELIOS_PATH}/previews/<branch-slug>` | `${HELIOS_URL}/previews/<branch-slug>/` |

Для доступа используются секреты репозитория: `HELIOS_SSH_KEY`, `HELIOS_KNOWN_HOSTS`, `HELIOS_USER`, `HELIOS_HOST`, `HELIOS_PORT`, `HELIOS_PATH`, `HELIOS_URL`.

## Контроль качества

После публикации выполняется healthcheck:

| Проверка | Условие успеха | Поведение при ошибке |
|---|---|---|
| HTTP-код | опубликованный URL возвращает `200` | job завершается с ошибкой |
| Контрольная строка | HTML содержит `Результаты исследований` | job завершается с ошибкой |

## Откат

Перед каждой публикацией текущая версия сохраняется в `${HELIOS_PATH}/.rollback/<scope>/<timestamp>`, а новая сборка дополнительно сохраняется в `${HELIOS_PATH}/.releases/<scope>/<timestamp>`.

Откат выполняется ручным запуском workflow `Deploy MkDocs` с параметрами:

| Параметр | Значение |
|---|---|
| `rollback` | `true` |
| `rollback_ref` | `latest` или имя каталога с timestamp |

При откате содержимое выбранной резервной копии синхронизируется обратно в целевой каталог, затем повторяется healthcheck.

## Сравнение GitHub Pages и Helios

| Критерий | GitHub Pages | Helios |
|---|---|---|
| Время доставки | Обычно быстрее за счёт встроенного `deploy-pages` и отсутствия SSH-копирования | Зависит от скорости SSH-сессии и количества файлов |
| Надёжность | Управляемая платформа с атомарной публикацией Pages artifact | Зависит от SSH-доступа, квоты и состояния пользовательского каталога |
| Отладка | Удобные логи Actions и понятные ошибки Pages deployment | Требуется анализ `rsync`, прав на каталог и доступности опубликованного URL |
| Preview-сборки | Требуют отдельной логики или окружений | Реализуются прямой публикацией веток в подкаталоги |
| Откат | Обычно через повторный деплой старого коммита | Реализован сохранением предыдущего каталога на Helios |

## Обрыв развёртывания

Сборка сначала загружается в отдельный release-каталог, затем синхронизируется в целевой каталог. Если обрыв произошёл до финальной синхронизации, опубликованная версия остаётся прежней. Если обрыв произошёл во время финальной синхронизации, healthcheck должен завершить job с ошибкой, а возврат выполняется через ручной rollback на последнюю сохранённую копию.
