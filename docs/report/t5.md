# Т5. Публикуемость и цитируемость результата

## Введение

В рамках данного исследования проанализированы механизмы обеспечения публикуемости, авторитетности, цитируемости и долгосрочной доступности результатов научных исследований в вебе. Рассмотрены постоянные ссылки, версионирование артефактов, присвоение DOI и привязка к ORCID, структурированные метаданные (Google Scholar / Highwire Press, Dublin Core, Open Graph, sitemap.xml, robots.txt), раздельное лицензирование и соответствие принципам FAIR. Проведён анализ поддержки этих механизмов генераторами статических сайтов из T1 (MkDocs, Sphinx, Pelican, Quarto) и достижимости на хостинге Helios ИТМО.

## 1. Постоянные ссылки и стабильность URL при пересборке

### Проблема «гниения ссылок» (Link Rot) в научных публикациях
В академической среде стабильность ссылок критична. Ссылка из статьи на веб-ресурс, возвращающая `404 Not Found` спустя год после публикации, обесценивает возможность проверки гипотез и воспроизведения экспериментов.

### Механизмы обеспечения стабильности URL:
1. **Каноническая структура каталогов (`use_directory_urls`)**:
   - URL вида `https://domain/experiments/` вместо `https://domain/experiments.html`.
   - Сервер отдаёт `index.html` внутри каталога, что позволяет менять расширения или внутренний генератор без изменения публичного URL.
2. **Абсолютные канонические теги (`<link rel="canonical" href="...">`)**:
   - Предотвращают дублирование страниц в поисковых индексах (например, версий со слэшем и без, HTTP и HTTPS, зеркал).
   - В MkDocs формируются автоматически при указании параметра `site_url`.
3. **Стабильные псевдонимы версий (aliasing)**:
   - Использование постоянного алиаса `latest/` для последней актуальной версии и фиксированных неизменных адресов для тегов (`v1.0/`, `v1.1/`).
4. **Редиректы при реструктуризации**:
   - При переносе разделов должны настраиваться HTTP 301 редиректы (через серверные конфигурации Nginx/Apache `.htaccess`, либо плагины генерации HTML-редиректов, например, `mkdocs-redirects`).

## 2. Версионирование сайта и соответствие версий сайта, кода и данных

Публикуемый результат исследования — это триада: **Сайт (описание/визуализация) $\leftrightarrow$ Код эксперимента $\leftrightarrow$ Исходные данные**.

```
[ Git Tag v1.1 ] 
       │
       ├──► Код репозитория (коммит e.g. a844c34)
       ├──► Версия данных (SHA-256 хеш датасета в experiment.json)
       └──► Версия сайта (mike deploy v1.1 latest) ──► URL: /pyweb/v1.1/
```

### Способы поддержания согласованности:
- **Инструменты мультиверсионности документации**:
  - `mike` для MkDocs: сохраняет каждую версию сайта в отдельную ветку (`gh-pages`), раскладывая сборки по каталогам `vX.Y/` и генерируя `versions.json`.
  - `sphinx-multiversion` для Sphinx: собирает страницы по тегам и веткам git.
- **Инъекция метаданных сборки**:
  - При сборке в CI скрипт конвейера фиксирует хеш коммита (`git rev-parse --short HEAD`), дату сборки и контрольную сумму входных датасетов (`SHA-256`), помещая их в `_data/build_info.json`.
  - Шаблонизатор (Jinja2 / macros) выводит эти данные в подвал каждой страницы или карточку эксперимента (реализовано в заданиях P3 и P5).

## 3. Присвоение DOI и указание ORCID

### Присвоение DOI (Digital Object Identifier)
DOI — глобальный постоянный идентификатор научного объекта, разрешаемый через `https://doi.org/...`.

#### Механизм связки GitHub + Zenodo:
1. Репозиторий связывается с сервисом **Zenodo** (или Figshare) через OAuth.
2. В репозитории включается вебхук для отслеживания событий релизов.
3. При создании GitHub Release (`git tag v1.0.0 && git push --tags`) Zenodo:
   - Автоматически архивирует снимок репозитория в формате `.zip`.
   - Присваивает снимку уникальный неизменяемый DOI (например, `10.5281/zenodo.XXXXXXX`).
   - Формирует метаданные для DataCite и индексаторов.
4. На сайт помещается бейдж с DOI:
   ```markdown
   [![DOI](https://zenodo.org/badge/DOI/10.5281/zenodo.1234567.svg)](https://doi.org/10.5281/zenodo.1234567)
   ```

### Указание ORCID (Open Researcher and Contributor ID)
ORCID (16-значный идентификатор) устраняет неоднозначность авторов с одинаковыми фамилиями.

#### Правильное оформление на сайте:
1. **Визуальное отображение**:
   ```html
   <a href="https://orcid.org/0009-0008-8411-477X" target="_blank" rel="noopener noreferrer">
     <img alt="ORCID logo" src="https://info.orcid.org/wp-content/uploads/2019/11/orcid_16x16.png" width="16" height="16" />
     0009-0008-8411-477X
   </a>
   ```
2. **Файл CITATION.cff**:
   В корень репозитория помещается файл в формате Citation File Format (поддерживается GitHub и Zenodo для автоматического цитирования):
   ```yaml
   cff-version: 1.2.0
   message: "If you use this software or data, please cite it as below."
   authors:
     - family-names: "Бобрусь"
       given-names: "Александр"
       orcid: "https://orcid.org/0009-0008-8411-477X"
   title: "Исследование генераторов статических сайтов и CI/CD конвейеров"
   version: "1.1.0"
   date-released: "2026-10-30"
   ```

## 4. Метаданные для индексации и поиска

Для того чтобы научные агрегаторы и поисковые системы корректно интерпретировали сайт, в разметку HTML внедряются специализированные теги метаданных.

### Highwire Press теги (для Google Scholar)
Google Scholar сканирует страницы и ищет метатеги семейства Highwire Press. Без них страница индексируется как обычный веб-сайт, а не академическая работа:
```html
<meta name="citation_title" content="Исследование характеристик затухающих колебаний">
<meta name="citation_author" content="Бобрусь, Александр">
<meta name="citation_publication_date" content="2026/10/30">
<meta name="citation_pdf_url" content="https://bobrall.github.io/pyweb/paper.pdf">
<meta name="citation_doi" content="10.5281/zenodo.1234567">
```

### Dublin Core (DC)
Стандарт описания цифровых ресурсов (ISO 15836):
```html
<meta name="DC.title" content="Результаты исследований: Лабораторная работа">
<meta name="DC.creator" content="Александр Бобрусь">
<meta name="DC.date" content="2026-10-30">
<meta name="DC.publisher" content="Университет ИТМО">
<meta name="DC.type" content="Text.ScientificWork">
<meta name="DC.format" content="text/html">
<meta name="DC.identifier" content="https://bobrall.github.io/pyweb/">
```

### Open Graph и Twitter Cards (для социальных сетей и мессенджеров)
Формируют превью ссылки при отправке в Telegram, Slack, соцсети:
```html
<meta property="og:type" content="article">
<meta property="og:title" content="Результаты исследований — Лабораторная работа">
<meta property="og:description" content="Автоматизированный конвейер публикации экспериментов">
<meta property="og:url" content="https://bobrall.github.io/pyweb/">
<meta property="og:image" content="https://bobrall.github.io/pyweb/assets/preview.png">
```

### Карты сайта и инструкции поисковым роботам
- `sitemap.xml`: список всех доступных страниц сайта с датой их последней модификации (`<lastmod>`), генерируется MkDocs автоматически.
- `robots.txt`: правила доступа краулеров. Разрешает обход основных страниц и запрещает сканирование служебных preview-директорий:
  ```txt
  User-agent: *
  Allow: /
  Disallow: /previews/

  Sitemap: https://bobrall.github.io/pyweb/sitemap.xml
  ```

## 5. Раздельное лицензирование (текст, код, данные)

Смешение лицензий (например, распространение всего репозитория под MIT или GPL) непригодно для научных проектов.

| Объект | Рекомендуемая лицензия | Назначение и причины выбора |
|---|---|---|
| **Код** (скрипты, пайплайны, веб-интерфейс) | **MIT** / Apache 2.0 | Разрешительная лицензия; допускает свободное использование, модификацию и интеграцию алгоритмов в другие проекты без юридических рисков. |
| **Текст и графика** (статьи, отчеты, графики) | **CC BY 4.0** | Требует обязательного указания авторства (атрибуции) при цитировании, что соответствует нормам академической этики. Не накладывает ограничений на переработку. |
| **Данные** (датасеты, замеры) | **CC0 1.0** / ODC-By | Данные как факты не подлежат авторскому праву во многих юрисдикциях; CC0 снимает все барьеры на повторный анализ, объединение с другими датасетами и обучение моделей. |

В данном проекте раздельное лицензирование реализовано наличием файлов `LICENSE` (MIT) и `LICENSE-CONTENT` (CC BY 4.0), а также отдельным разделом сайта `licenses.md`.

## 6. Соответствие принципам FAIR

Принципы FAIR определяют требования к научной инфраструктуре:

1. **Findable (Находимость)**:
   - Каждому исследованию присвоен постоянный идентификатор (DOI, стабильный URL).
   - Присутствуют подробные метаданные (Dublin Core, Highwire Press).
   - Наличие `sitemap.xml` и индексация поисковыми системами.
2. **Accessible (Доступность)**:
   - Протоколы доступа открытые и бесплатные (HTTPS, git).
   - Метаданные остаются доступными даже при удалении или архивации самих данных.
3. **Interoperable (Совместимость)**:
   - Данные и результаты хранятся в общепринятых машиночитаемых форматах (CSV, JSON, BibTeX).
   - Используются стандартные онтологии и схемы метаданных.
4. **Reusable (Переиспользуемость)**:
   - Наличие четкого раздельного лицензирования.
   - Подробное описание методологии проведения эксперимента и версий инструментов в `methodology.md`.

## 7. Сравнительный анализ механизмов публикации в генераторах из T1

| Механизм | MkDocs (Material) | Sphinx (MyST) | Pelican | Quarto |
|---|---|---|---|---|
| **Постоянные URL (`use_directory_urls`)** | ✅ «Из коробки» | ⚠️ Требует настройки `dirhtml` билдера | ⚠️ Через `ARTICLE_URL = '{slug}/'` | ✅ «Из коробки» |
| **Канонические ссылки (`canonical`)** | ✅ «Из коробки» (через `site_url`) | ⚠️ Плагин `sphinxcontrib-canonical` | ⚠️ В шаблоне темы | ✅ «Из коробки» |
| **Версионирование сайта** | ⚠️ Плагин / CLI `mike` | ⚠️ Расширение `sphinx-multiversion` | ❌ Вручную | ⚠️ Вручную (через профили) |
| **Присвоение DOI (Zenodo release)** | ⚙️ Вручную (на уровне Git/GitHub) | ⚙️ Вручную (на уровне Git/GitHub) | ⚙️ Вручную (на уровне Git/GitHub) | ⚙️ Вручную (поддержка `citation` в YAML) |
| **Citation metadata (`CITATION.cff`)** | ⚙️ Вручную (файл в корне) | ⚙️ Вручную (файл в корне) | ⚙️ Вручную (файл в корне) | ✅ Генерирует автоматически |
| **Google Scholar (Highwire Press)** | ⚠️ Через theme overrides (`extra_head`) | ⚠️ Через `html_context` или плагин | ⚠️ Правка Jinja-шаблона | ✅ «Из коробки» (`citation: true`) |
| **Dublin Core & Open Graph** | ⚠️ Open Graph — плагин `material/social`; DC — overrides | ⚠️ Через метатеги шаблона | ⚠️ Через плагины темы | ✅ Встроенная генерация |
| **`sitemap.xml`** | ✅ «Из коробки» | ⚠️ Расширение `sphinx-sitemap` | ⚠️ Плагин `sitemap` | ✅ «Из коробки» |
| **`robots.txt`** | ⚙️ Вручную (`docs/robots.txt`) | ⚙️ Вручную (`_static/robots.txt`) | ⚙️ Вручную | ⚙️ Вручную |
| **Раздельное лицензирование** | ⚙️ Вручную (конфигурация страниц) | ⚙️ Вручную (страницы документации) | ⚙️ Вручную | ⚙️ Вручную |
| **Экспорт в PDF/A для архивации** | ⚠️ Плагин `mkdocs-with-pdf` | ✅ Билдер `latexpdf` «из коробки» | ❌ Только сторонние утилиты | ✅ Встроенный рендерер PDF (Typst/LaTeX) |

**Категории реализации:**
- **«Из коробки» (✅)**: доступно сразу после установки ядра генератора или базовой темы.
- **Требует плагина (⚠️)**: требует установки дополнительного Python-пакета или внешней утилиты.
- **Только вручную (⚙️)**: функциональность не автоматизирована генератором сайта и создается разработчиком вручную (настройка Git, размещение файлов, правка HTML-шаблонов темы).

## 8. Реализуемость требований цитируемости на Helios ИТМО

Сервер Helios ИТМО представляет собой студенческий хостинг со статическим веб-сервером (Apache/Nginx) и SSH-доступом в пользовательский каталог `~/public_html`.

### Что достижимо на Helios:
1. **Статические файлы метаданных**:
   - `sitemap.xml` и `robots.txt` успешно раздаются веб-сервером Helios при размещении в корне каталога публикации.
   - Метатеги Google Scholar, Dublin Core и Open Graph вшиты непосредственно в скомпилированный HTML-код страниц и полностью доступны для краулеров.
2. **Версионирование в подкаталогах**:
   - На Helios возможна публикация версий в каталоги `~/public_html/v1.0/`, `~/public_html/v1.1/` и `~/public_html/latest/` посредством скрипта `rsync`.
3. **Раздельное лицензирование и данные**:
   - Файлы лицензий, исходные CSV-датасеты и страницы экспериментов полноценно обслуживаются по HTTPS.

### Что недостижимо (или ограничено) на Helios:
1. **Собственный домен и валидный сертификат**:
   - Helios выдает сайты только по фиксированному пути вида `https://se.ifmo.ru/~username/`. Привязать произвольный исследовательский домен (например, `lab.example.org`) невозможно.
2. **Управление редиректами на уровне сервера**:
   - Если серверная конфигурация запрещает `.htaccess` (или переопределение директив `AllowOverride None`), организация постоянных HTTP 301 редиректов становится невозможной, приходится полагаться на `<meta http-equiv="refresh">` или клиентский JavaScript.
3. **Интеграция с автоматическим выпуском DOI**:
   - DOI регистрируется в Zenodo только на базе публичных git-репозиториев (GitHub/GitLab). Helios является конечной точкой раздачи статических файлов и не имеет API для прямого выпуска DOI.
4. **Управление заголовками HTTP (Header Control)**:
   - Нет возможности настроить специализированные HTTP-заголовки связывания (`Link: <...>; rel="canonical"`, `Link: <...>; rel="describedby"`).

## Вывод

Для обеспечения максимальной цитируемости и соблюдения принципов FAIR оптимальным решением является:
1. **Quarto** или **MkDocs (с расширениями)** в качестве ядра сайта благодаря богатой экосистеме метатегов и структурированных данных.
2. **Связка GitHub + Zenodo** для автоматического присвоения постоянных идентификаторов DOI на каждый выпуск версии (`git tag`).
3. Размещение метаданных автора с **ORCID** и спецификацией **CITATION.cff** в корне репозитория.
4. Основная публикация на платформе с возможностью закрепления постоянных URL (GitHub Pages / домен института), с резервным зеркалированием на **Helios ИТМО** с соблюдением требований `robots.txt` и `sitemap.xml`.
